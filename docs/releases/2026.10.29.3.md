# Release 2026.10.29.3 — task workflows

Admin-only React Flow designer and Elsa Workflows Core 3.9 execution. Curated nodes: start, task assignee/approver binding, work submission, approval/rejection, safe condition, additional notification, persisted minute delay, close and end. No arbitrary executable expressions or public Elsa management endpoints.

Drafts can be saved incomplete. Publishing validates the graph and makes it immutable. Activation selects one version per company/project; a project definition takes precedence over the company default. Only new tasks receive the active version. No published matching definition means legacy behavior. No production definitions are automatically published by this release.

Human actions use existing company/project permissions. Only the task approver or Admin can approve/reject. Admin can explicitly bypass one instance with a reason. Submitted output is preserved on approval. All branch execution, task changes, instance state and notice outbox changes share the application's database transaction. External notification delivery remains asynchronous. Graph notifications supplement existing task-event notices.

Only two new tables are added: FlowDefinitions and FlowRuns. Existing task columns/statuses are unchanged. Elsa bookmarks and workflow state persist in FlowRuns. The timer worker resumes due bookmarks every 30 seconds. Execution is sequential; each output has exactly one connection. Approvals must lead to close without another wait. Assignment uses the people selected on the task form.

## Rollback

- Activate an earlier published definition for future tasks in the designer. Existing instances keep their pinned version.
- Disable a definition to stop new assignments (company default still applies when a project override is disabled).
- Admin can bypass one task with a reason in task details; ownership restrictions still apply.
- Emergency application rollback on this server:

  `bash /opt/taskmanagment/releases/2026.10.29.3/rollback.sh --apply`

  Run with `--check` first for a non-mutating prerequisite check. The script moves Waiting runs to Bypassed, increments their concurrency revisions, restores the previous Compose file and starts the retained 2026.10.29.2 API/frontend images. Existing/new task data remains. No automated database restore occurs.
- Verified pre-release SQL backup: `TaskManagement.before.bak` in the protected server release directory. `RESTORE VERIFYONLY WITH CHECKSUM` passed. Restoring it is a separate disaster-recovery operation requiring an explicit decision because it would discard later writes.
- `WorkflowEngine__Enabled=false` is a temporary server switch. Before re-enabling after legacy edits, bypass affected instances; the rollback script handles this automatically.

## Validation

Local disposable DB: create/submit/approve/reject; published immutability and optimistic revisions; version pinning/reactivation; prohibited approval bypass; supervisor/assignee denials; atomic rollback when a task has open children and successful retry; persisted timer and bookmarks across process restart; conditional branch/merge and queued in-app notice; concurrent approvals commit once. Actual previous application binaries ran on an upgraded database copy and edited newly managed tasks successfully.

Existing suites: 33 permission checks, authentication/company isolation and legacy SQLite upgrade regressions, SMTP loopback/module checks, six frontend tests, production TypeScript/Vite build. Browser verified draft save, publish and read-only graph. Tests never send production SMS/email or create production tasks.

API restart requires users to sign in again because sessions are currently held in memory.
